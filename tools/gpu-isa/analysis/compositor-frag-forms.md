# Compositor fragment programs: forms, work list for the decoder, and the sampled textures

Agent J, 2026-11-19. Generated by `tests/frag_forms.c` (run `wsl -u root -d Ubuntu -- bash tests/r6.sh`; raw output in `logs/_frag_forms.txt`, `logs/_tex_res.txt`) from capture17
(sessions 8, 10) + capture18 (sessions 1, 9..14), program bytes merged across snapshots (a byte zero in one capture is taken from another). Draws and slots come from
`core/s8gfx_stream.h` (analysis/compositor-stream.md). Instruction lengths from `s8f_len`; the forms marked *assumed* are lengths guessed here.

## 0. Findings

1. **capture18 lost the main program heap.** The boot-arg `s8agxnores=10,117,103,98,68,69,70,71` removes resource 10 = VA 0x1000e0000 (0x50000), the heap that holds most
   vertex programs (0x1000e1830 ...) and the block-style fragment programs (0x1000e16b0 ...), and 98 = 0x1009d0000, the uniform ring of the capture17 layout. In capture18 the ids shifted
   (res_102 = 0x100a60000 is now the vertex/index/uniform ring, res_103 = IOSurface 2): the skip list hits the wrong things. What capture18 DOES add: session 1 intact -> res_3 (builtin programs
   0x10002xxxx), res_59 (0x100610000), res_72..76 first dump, res_4, res_11..25. Merged with capture17's res_10 (sessions 3-5, partial) most programs are now present, but a clean frame needs res_10
   dumped. **Fix: remove 10 and 98 from `s8agxnores`** (keep 68-71, 117; 103 is the IOSurface now and costs nothing; add the id of the 0x100a60000 ring, res_102, to the *dump* list).
2. Of 91 distinct fragment program entries seen in the draws of those 9 snapshots: 38 walk to `08 01`; 8 stop at a form `s8f_len` does not know (reliable start: program block or a
   walk that reaches the entry); 26 have no determinable start (no `c0400038` block record and the entry is in the middle of the program: the preamble is not reachable from an address
   we know); 19 have zero bytes (res_75..76 0x1006df000 / 0x10070e000 / 0x10073e000 = programs of the large heaps whose later pages were never dumped).
3. Program image layout (new): `c0400038 <block>` gives the image start; header (usually 0x40 bytes: `0d000105 0012c000 028a0038 200400c0 10400402 00080108 00080008 ...`) then code at
   block+0x40. The entry pointer sits after the pre-code (tile load / texture fetch preamble) at code +0x10 / +0x20 / +0x30 / +0x70 (bits: `entry & 3` = 2 for fragment, and for 5 programs the instruction
   boundary is entry+2). Some images use a different header (`80010051 00100000 ...`, block 0x1000e0040): code does not start at +0x40 there (stops at op 0x80 in the table: header data, not an opcode).
4. The compositor's fragment programs are of three families: (a) **constant/solid** (`51 iter, 48 wait_pix, 89 st_tile, 08 01`, 0x1c bytes) and **pass load/store programs** in res_17 slots (0x10012ef50 =
   `42 00 08 00 42 02 0a 00 89 .. f0 ff 08 01`: store of r0..r1), (b) **textured blend** (`48 wait_pix, f9 ld_tile, 92 mov_imm16, f6 f16_ffma .., 51 iter, 21 texture_sample, 38 wait, f6 f16 ffma tree, 86 f16 fadd .., 89 st_tile`)
   with ~212 f16 `c6` + 112 `f6/76` ffma instructions in total, (c) **MSAA-resolve-like** (four-way `79 ld_tile .. fc 01`, tree of `c6`, pixel write `31`).
