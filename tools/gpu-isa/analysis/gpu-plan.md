# GPU plan: Mali-G71 MP20 (Exynos 8895) for iOS 16.7 on the Galaxy S8

Legend: [E] = evidence read in a file (path given), [G] = guess / from memory, to be verified.
Refs: S9+ = C:\github\ios-s8\ref\s9plus (read only, never executed). Baseline = C:\github\ios-s8\upstream. Samsung = C:\github\ios-s8\samsung-src.
Paths under S9+ are relative to ref\s9plus\.

## 0. Key conclusions

1. [E] The S9+ port does NOT use CoreAnimation's CPU renderer, and does NOT replace AGX. It lets CoreAnimation's own GLES renderer run in backboardd by replacing the `EAGLContext` methods with a dylib (`libhakios.gl.dylib`) that sits on Mesa (OSMesa interface with an ES profile) whose Panfrost driver talks to a small XNU IOKit service that is a re-implementation of the Linux panfrost DRM ioctl interface.
2. [E] The kernel GPU driver is not a ported Arm kbase and not Linux panfrost. It is HakiOS's `RedwoodMali` (written for a MediaTek Mali-G52), about 2200 lines C + 850 lines C++ (`core/drivers/gpu/hakios.mali.c`, `hakios.mali.cpp`), APSL-2.0. It is polling-based (no interrupts), one job at a time, one address space (AS0) for all clients. So the kernel part is small and portable to the G71.
3. [E] The 8895 GPU is NOT at 0x14AC0000. Samsung DTS says `mali@13900000`, size 0x5000 (exynos8895.dtsi:777). IRQs are SPI 60 (JOB), 61 (MMU), 59 (GPU), i.e. GIC INTID 92/93/91 [E for SPI numbers; INTID = SPI+32 is standard GIC].
4. [E] Even the S9+ port, with a working GPU, says: heavy SpringBoard widget/blur scenes still stall, sustained 60 FPS not established. So expect GLES-through-Panfrost to give a large win over 4x A53 CPU rendering, but not a smooth iOS.
5. Biggest unknowns: (a) the G3D power sequence on 8895 (clock/PMU/PMIC/bus protection) has never been run by us; (b) Mesa Panfrost on G71 quality; (c) Cortex-A53 only 512 MiB RAM and GPU is non-coherent, cache maintenance cost.

### 1.2 What does not work (their words, [E])
- README.md: "Heavy SpringBoard widget/blur scenes still stall; sustained 60 FPS is not established", "substantial animation and touch latency", WebGL 3D not working, camera/audio/cellular/App Store not qualified.
- Mali-G72 clock: runs only 260/455/572 MHz; SM-G965F ASV tops out at 750 mV. `mali_gov=1` crude load governor in driver. No real power management.
- `hakios.mali.cpp`: "Not here yet: an address space for each program, interrupts, buffers shared between programs as file descriptors."
- Of the ~90 CoreAnimation fragment "functions" its GLES renderer lacks about half (the Metal renderer has all); missing ones are drawn with no program through `plain_draw_begin()` hack; `vblur=0/2` switches turn variable-radius blur off or paint it from masks (materials/blur are the weak spot).
- The kernel GPU driver was derived from a G52 driver and the S9+ code itself said "Here it has not run" at the time of the header; installed profile says `mali_step 9`, `hardware_tested true`, so it now runs.
- Security: G1 in `core/docs/driver-review/gpu-display.md` is about Adreno path but the same design: user command buffers unvalidated.

### 1.3 Power/clock lessons from S9+ that probably transfer [E, hakios.mali.c header]
- Raise the G3D rail BEFORE the first GPU register access. S-Boot leaves BUCK6 at 644 mV with 260 MHz and on S9+ that combination hangs the GPU (DATA_INVALID_FAULT, SoC hang if registers read before rail up).
- Reading GPU registers while domain is off is a bus hang, not an error.
- PLL_CON2 must be 0x30000003 while locking (S-Boot's 0x10000001 never reaches STABLE).
- After power-on an SMC (0x82000410) to restore DTZPC protection was needed (S9 under Carbon hypervisor, EL3); without it the first access gave an SError. S8 equivalent unknown [G].
- Switch G3D mux to 26 MHz osc while reprogramming PLL, PLL M/P/S limits (VCO 600-1200 MHz).
- Power off needs five low-power PMU settings or domain half-off (STATUS 0x002F000E). We can simply never power off.
- GPU is non-coherent with CPU caches: COHERENCY_ENABLE=31 after every reset; kernel cleans cache around job pages; user buffers write-combined; cached IOSurface needs explicit DC CIVAC (163 ms per 12 MiB per-line trap - bad).
- Their GPU VA: 32 MB..4 GB, code BOs never cross a 16 MB line (Mesa/Bifrost assumption).

## 4. Concrete staged plan

### Stage 0: read-only probe in our dreamlte shim loader (effort: 2-4 days; risk: medium: an SoC bus hang kills the boot but is recoverable via TWRP)

Rules from S9+ experience: never read a GPU register unless PMU status says G3D is on and the rail/clock were set; log every step to the ramoops/ring log BEFORE the next write; add a step counter in the boot args so each boot goes one step further (S9+ `mali=N`).

Step 0a (pure reads, zero risk of hang; do first in one boot):
- PMU 0x16480000+0x40E0, +0x40E4, +0x40E8 (G3D config/status/option).
- CMU_G3D 0x13800000: +0x0 LOCKTIME, +0x100, +0x120, +0x124, +0x128, +0x140..+0x150, +0x1000, +0x1800, +0x1804, +0x201c. (Reading CMU_G3D itself: S9+ says it lives outside the domain and keeps settings, "[G] for 8895"; if the first read hangs, stop.)
- PMIC BUCK6 B6CTRL/B6OUT1/B6OUT2 (0x23..0x25) via existing `speedy()` in `shim/dreamlte/pmic.c`, convert: uV = 300000 + 6250 * val.
- Is S-Boot leaving G3D on? (status == 0xF) That tells us if step 0b is even needed.

Step 0b (power-up, only if off):
```c
#define PMU      0x16480000UL
#define CMU_G3D  0x13800000UL
#define G3D      0x13900000UL
static inline uint32_t rd(uintptr_t a){ return *(volatile uint32_t*)a; }
static inline void wr(uintptr_t a,uint32_t v){ *(volatile uint32_t*)a=v; __asm__ volatile("dsb sy"); }

// 1. rail first (Samsung: uV = 300000 + 6250*sel); choose 800000 uV (sel 0x50 = 80 -> 800000)
speedy(SLAVE_PMIC, B6OUT1 /*0x24*/, 1, 0x50);   // verify against B6CTRL mode first
// 2. replay Samsung g3d_on (pmucal_local_exynos8895.h:357-362)
wr(CMU_G3D+0x148, 0x30000003);
wr(CMU_G3D+0x140, rd(CMU_G3D+0x140) | (1u<<4));
wr(CMU_G3D+0x100, rd(CMU_G3D+0x100) | (1u<<4));
wr(PMU+0x40E0, (rd(PMU+0x40E0) & ~0xFu) | 0xF);
for (t=0; t<TIMEOUT && (rd(PMU+0x40E4)&0xF)!=0xF; t++) udelay(10);
if ((rd(PMU+0x40E4)&0xF)!=0xF) { log("g3d not on"); return; }
// 3. bus dividers as S9+ did: MUX_CLK_G3D_BUSD(+0x1000)=0 (PLL), DIV_CLK_G3D_BUSP(+0x1804)=3, wait busy bit16
```
Open risk: the PLL must be programmed and STABLE (M/P/S at the proper CON0 offset, 0x120 vs 0x140 ambiguity) before the mux selects it; if S-Boot left the PLL running, skip PLL programming.
Open risk: is there a TrustZone/DTZPC protection to restore (S9+ needed SMC 0x82000410 under Carbon EL2/EL3)? The S8 shim runs at EL? with Samsung's S-Boot->EL3 [G]; if the first GPU read gives an SError, try PSCI-SMC or an equivalent SMC. Install an exception vector in the shim that logs ESR/FAR on SError so we get an answer instead of a hang (check `shim/start.S`).

Step 0c (GPU reads; MMU off or identity, physical address direct):
```c
uint32_t id = rd(G3D+0x000);               // GPU_ID, expect 0x6000xxxx (G71) in [31:16]
log("GPU_ID", id);
log("L2_FEATURES", rd(G3D+0x004)); log("TILER_FEATURES", rd(G3D+0x00C));
log("MEM_FEATURES", rd(G3D+0x010)); log("MMU_FEATURES", rd(G3D+0x014));
log("AS_PRESENT", rd(G3D+0x018)); log("JS_PRESENT", rd(G3D+0x01C));
log("GPU_IRQ_RAWSTAT", rd(G3D+0x020)); log("GPU_STATUS", rd(G3D+0x034));
log("COHERENCY_FEATURES", rd(G3D+0x300));
log("THREAD_MAX_THREADS", rd(G3D+0x0A0)); ...
log("SHADER_PRESENT lo/hi", rd(G3D+0x100), rd(G3D+0x104));
log("TILER_PRESENT", rd(G3D+0x110)); log("L2_PRESENT", rd(G3D+0x120));
// soft reset + L2/shader power:
wr(G3D+0x024, 0xFFFFFFFF);                 // GPU_IRQ_CLEAR
wr(G3D+0x030, 1);                          // GPU_COMMAND = SOFT_RESET
poll GPU_IRQ_RAWSTAT & (1<<8) (RESET_COMPLETED), timeout 100 ms
wr(G3D+0x304, 31);                         // COHERENCY_ENABLE = none
wr(G3D+0x1E0, l2_present);  poll L2_READY (+0x160)
wr(G3D+0x180, shader_present); poll SHADER_READY (+0x140)
wr(G3D+0x190, tiler_present);  poll TILER_READY (+0x150)
```
(register offsets are standard Mali JM [G]; the S9+ driver uses the same, `hakios.mali.c` steps 4-6 [E]; verify each against panfrost_regs.h before use.)
Success criterion: GPU_ID >> 16 == 0x6000 (or whatever G71 reports), shader present popcount 20, all READY masks reached.

### Stage 1: XNU kernel driver `SweetMali` (effort: 3-5 weeks for steps 1.1-1.4; risk: high)
Base: our kernel already has SweetSurface (IOSurface) and SweetFramebuffer (IOMFB) in patch 0046. Use the S9+ HakiosMali shape (also panfrost ioctl-compatible so the S9+ drm shim and Mesa patches can be reused as concepts):
1.1 IOService with MMIO `ml_io_map(0x13900000, 0x5000)`, power sequence from Stage 0 moved into kernel (once; keep GPU on forever initially).
1.2 GPU page tables AS0: AArch64 4K format (Mali `AS_TRANSTAB`, `AS_MEMATTR`, `AS_COMMAND`), BO mapping, cache clean (`FlushPoC_DcacheRegion` equivalent); reuse S9+ VA rules (32 MB-4 GB, no crossing 16 MB for code BOs).
1.3 Job submission: JS0/JS1 (`JS_HEAD_NEXT`, `JS_CONFIG_NEXT`, `JS_COMMAND_NEXT`), polled first (S9+ does this), then interrupts (SPI 59/60/61 via the GIC; our kernel has GIC-400 working).
1.4 IOKit user client with panfrost-style selectors (get_param, create_bo, mmap_bo, submit, wait) + IOSurface-as-BO selector (S9+ 0x7c) + fence on IOSurface (`maliSeq`).
1.5 Fault handling, reset-on-hang, a watchdog; memory: only 512 MiB RAM now, GPU BOs are wired - budget carefully (IOSurface 1440x2960x4 = 17 MB each; triple buffering plus CA layer surfaces will eat RAM quickly).
First test = their `mali_test`-style: two jobs (write value; same through page tables) before Mesa.

### Stage 2: user space (effort: 4-8 weeks; risk: high)
2.1 Cross-build Mesa (25.x, panfrost + softpipe first) with `xnu-clang`-like toolchain and iPhoneOS 16.x SDK into libOSMesa.dylib; reuse the idea of libdrm shim over IOKit; patch pan_kmod expectations (BO flags, fences). Check G71 in Mesa's model table first; run softpipe as reference, compare.
2.2 `libhakios.gl` equivalent: EAGLContext method replacement in backboardd + vtable patches at hard-coded dyld-shared-cache addresses of 20H392 (ours are different from 20F66's, must be re-derived - this is much work and fragile). Our userland is 16.7.16 (20H392) of iPhone X (D22), S9+ is 16.5 (20F66) of iPhone X too, so same device but different cache build.
2.3 IOSurface <-> GL texture import (`EGLImage` from IOSurface id) with the kernel selector; fallback to copy.
2.4 Display: keep the existing CPU/DPP scan-out initially; later flip IDMA base address to the IOSurface the GPU just finished (zero copy). Our DECON/DPU facts are in `upstream` + the Samsung 8895 DPU (differs from 9810 `dpu_9810`: do not assume register layout equal).
Milestone order: triangle in a test app -> CA GLES renderer starts (the `renderer()` returns non-null) -> lock screen -> SpringBoard -> measured FPS.

### Stage 3: optimisation (effort: open-ended)
Interrupts instead of polling, real DVFS (reverse ACPM/ECT for G3D, or set PLL ourselves to 455/546 MHz), per-process AS, zero-copy IOSurface, cache-maintenance bulk range API (S9+ WIP says per-line trap = 163 ms / 12 MiB), blur/material shader coverage (the missing CA "functions"), AFBC, Mali tiler memory tuning. Realistic ceiling = what S9+ reports: usable but not 60 FPS in heavy scenes.

### What to verify first on the phone (in order)
1. Read-only dump of PMU G3D, CMU_G3D regs, BUCK6 (step 0a). Decides whether stage 0b is needed and resolves 0x120 vs 0x140 PLL offset question.
2. After power-on: first GPU_ID read does not SError/hang; it equals 0x6000xxxx.
3. SHADER_PRESENT (expect 20 bits), MMU_FEATURES, L2_PRESENT, whether reset completes; power up L2/shader/tiler.
4. Rail voltage: do not exceed 850 mV (dts max); lowest clock first.
5. Whether the iOS-side AMFI/dyld insert works for our backboardd (S9+ relies on a patched AMFI; we already run permissive AMFI per README).
6. Check Mesa version/G71 support on a host (read `pan_props.c`) before investing in stage 2.

## 6. Honest assessment
- The kernel half (stage 0 and 1) is a well-understood problem: a polling JM driver on a documented register set, with a close sample (S9+ HakiosMali) to read and relicense-compatibly adapt. The most likely blockers are SoC-specific: power/clock/protection (stage 0b) and the non-coherent cache cost.
- The user half is the hard part: Mesa cross-build for iOS is done upstream in S9+ (we can follow their scripts, not run them); making QuartzCore use the GLES renderer depends on private-API replacements and hard-coded shared-cache addresses of our exact iOS build, and the blur/material path is incomplete even in their working port.
- Expected gain: even S9+ with a working Mali-G72 reports stalls; but their CPU baseline is far faster than our 4xA53 at ~1 GHz with 512 MiB RAM, so the relative gain for us can still be large. RAM (512 MiB) may be the first limit once surfaces are wired for the GPU.
- Not evidence-verified here: G71 support level in current Mesa; GPU_ID value on this phone; 8895 PLL register map (two conflicting offset sets); whether a SMC/DTZPC fixup is needed; PMIC rail state left by S-Boot.
