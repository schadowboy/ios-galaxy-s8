## (1) Verdict on G71 support: YES in the source, but untested upstream

- [E] G71 is in the model table. HEAD `src/panfrost/model/pan_model.c:81`:
  `BIFROST_MODEL(PAN_PROD_ID(6, 0, 0), "G71", "G71", MODEL_ANISO(NONE), MODEL_TB_SIZES( 4096, 4096), MODEL_RATES(1, 1, 12))`. G72 is `PAN_PROD_ID(6,2,1)` on the next line. 25.0.7 `src/panfrost/lib/pan_props.c:61`: `MODEL(0x6000, 0, "G71", "TMIx", NO_ANISO, 8192, {})`. 25.3.0 and 26.0.0 still use `0x6000` (moved to `src/panfrost/model/pan_model.c`).
- [E] Arch v6 = Bifrost gen 1. HEAD `pan_model.h`: `pan_arch()` returns `PAN_ARCH_MAJOR(gpu_id)` (bits 31:28). `pan_screen.c:1169-1170` has `case 6: panfrost_cmdstream_screen_init_v6(screen)`. `src/panfrost/genxml/v6.xml` exists. Compiler has `bifrost_nir_options_v6` (`compiler/bifrost/bifrost_compile.h:172`, `pan_compiler.c:138`). Disassembler cmdline lists `{"G71", 6, 0}`.
- [E] Our GPU_ID decodes correctly in the NEW scheme (HEAD/26.3.0): 0x60a00001 -> arch_major 6, arch_minor 0, arch_rev 0xa (ignored), product_major 0 -> `PAN_PROD_ID(6,0,0)`. Match; `pan_get_model()` needs `min_core_count <= 20`, variant 0, no features: fine.
- [E] Trap for OLD scheme (<= 26.0.x incl. 25.0.7): `panfrost_get_model()` (25.0.7 `pan_props.c:89`) does an EXACT compare of `gpu_id` with 0x6000, and kmod builds `gpu_id = (GPU_PROD_ID<<16)|GPU_REVISION` / uses PROD_ID alone. The real register top half is 0x60a0 (arch_rev nibble 0xa), so the shim must report PROD_ID = 0x6000 for these versions (mask the 0x00f0 nibble) or screen creation fails with "panfrost: Unsupported model 60a0". For 26.3.0/HEAD report PROD_ID = 0x60a0 and REVISION = 0x0001 (raw `GPU_ID>>16` and `GPU_ID & 0xffff`). [G] for the exact masking rule; confirm by printing in the shim.
- [E] Docs: `docs/drivers/panfrost.rst` at HEAD and 26.3.0 lists "G71, G72 | Bifrost (v6) | GLES 3.1 | GL 3.1 | Vulkan 1.3 | CL 3.0". In 25.0.7, 25.2.0, 25.3.0 and 26.0.0 the same file still says "Other Midgard and Bifrost chips (e.g. G71) are not yet supported" (the table only had G72). So support for G71 appears in the docs only after 26.0 (26.3.0 has it). [E] CI only has a G72 job (`src/panfrost/ci/deqp-panfrost-g72.toml`, `gitlab-ci.yml:121`); there is no G71 CI. G71 correctness relies on "same arch v6 as G72" [G].
- [E] Reported GL level: `pan_screen.c:782` `essl_feature_level = arch >= 6 ? 320 : 310` (GLES 3.2 feature level on v6); docs say 3.1 conformant. GLES 3.0 for a compositor is fine. `fp16_const_buffers`, `sample_shading`, `indirect_temp_addr`, `fs_coord_pixel_center_integer` all on at arch >= 6.

## (2) Version to cross-build

Two realistic options:

A. mesa-25.0.7 (what S9+ used). Pros: S9+ patches (`core/tools/mesa/panfrost-darwin.patch`, `baseline-support/panfrost-cache-mapping.patch`, `panfrost-pack-pointer.patch`, osmesa-es-profile) apply as-is; OSMesa still exists. G71 table entry exists (0x6000, tilebuffer 8192). Cons: [E] G71 tile buffer is 8192 here vs 4096 in 26.3.0 (`MODEL_TB_SIZES(4096,4096)`), a later fix; with 8192 a 6-bpp tile could overrun the real 4096-byte buffer. Mitigation: patch the table to 4096 [G, needs check against Arm docs: G71 tile buffer 4KB is what 26.3.0 states]. Report PROD_ID=0x6000.

B. mesa-26.3.0 (newest tag found: mesa-26.2.x also exist; HEAD 27.0-devel). Pros: G71 documented, 4096 tilebuffer, rates table. Cons: OSMesa gone (see 5), S9+ patches would need porting (`pan_kmod.c/h`, `pan_bo.c`, `target osmesa`).

Recommendation: start with A (25.0.7 + S9+ patches + one-line model fix) to get the first triangle quickly; if G71 shader/tilebuffer bugs show up, retry with 26.3.0 [G]. 26.3.0 with EGL surfaceless is the long-term path.

## (3) Known G71 gaps and risks

- [E] G71 = arch 6.0, so `bi_quirks.h` sets `BIFROST_NO_FP32_TRANSCENDENTALS` (arch<7 && arch_minor<2) and `BIFROST_LIMITED_CLPER`. G72 (6.2) lacks the first quirk. The only CI-tested v6 GPU (G72) therefore does not exercise the G71 transcendental lowering path (exp2/log2/sin/rcp via other sequences). Highest compiler risk: wrong results for math-heavy shaders. A compositor (textures, blend, simple vec math) mostly avoids it.
- [E] v6-specific code paths: `pan_desc.c:88,157` (CRC on all RTs), `pan_desc.c:646/659` and `pan_fb.c:58-72` ("On v6 GPUs ... they *have* to pipeline", tile size cannot be doubled), `pan_fb_preload.c:236-241` (v6: Z/S-writing frame shaders can cause GPU timeouts, forward-pixel-kill workaround), `bifrost_compile.c:447` (v6 identity 0x688), `bi_schedule.c:2148` (v6 needs NOP clause). `pan_resource.c:798` bytes_per_pixel_max 6 on v6 else 4. `pan_afbc.c`: AFBC subblock paths gated on arch < 7. All shared with G72, so generally exercised by G72 CI.
- [E] G71 model: `MODEL_ANISO(NONE)` (no anisotropic filtering), no `min_rev_anisotropic`; texel/pixel rate 1.
- [E] 25.0.7 docs state G71 "not yet supported"; model table existed but upstream never validated it [E]; Mesa maintainers' own caveat that v6 behaviour is "no details" for MRT/empty tiles (`pan_desc.c:152,1250`).
- [E] Max threads: if GET_PARAM(MAX_THREADS)=0 Mesa assumes 384 on arch 6 and 64 regs/thread (`panfrost_kmod.c` `panfrost_dev_query_thread_props`). Real G71 values from kbase: report them. THREAD_FEATURES [31:24]=max tasks, [15:0]=registers.
- [G] MP20 (shader_present up to 20 bits). Mesa computes `core_id_range = fls(shader_present)` and TLS size from it (`pan_props.c`); no upstream limit seen, but G71 MP20 is the largest v6 core count; scratch/TLS BO size scales with it (20 cores * threads * TLS) so check memory use.
- [G] Possible unknowns for MIDGARD/BIFROST on Exynos: coherency (pan reports SELECTED_COHERENCY only from kmod >= 1.6; Exynos8895 G71 has none -> use NONE). Cache maintenance for cached CPU mappings is up to the kernel (S9+ chose write-combined/uncached mapping, see hakios_drm_map comment).
- [G] The S9 shim used a 1.2 interface version; G71 needs nothing newer.

## (4) Minimal kernel-interface contract (what Mesa needs from our XNU Mali driver)

How Mesa reaches the kernel [E]: `pan_kmod_dev_create(fd, ...)` loops over `backends[]` = panfrost, panthor (+virtio under HAVE_PANFROST_VDRM) (`pan_kmod.c`). panfrost's `dev_create` calls `pan_kmod_drm_drv_match(fd,"panfrost")` (drmGetVersion name) and requires version >= 1.1. There is no runtime plug-in API for a custom backend; `struct pan_kmod_ops` is a static table, and `panfrost_kmod_dev` has a small private ops struct {get_param, submit_job, bo_import, prime_fd_to_handle} that is only used inside panfrost_kmod.c / the virtio variants. Hence the S9+ approach (replace libdrm by `hakios.drm.c` so the stock panfrost backend works) is the right one; a patched backend is the other option.

### Version / identification
- `drmGetVersion(fd)->name == "panfrost"`, version 1.2 (as S9+) is enough; 1.3+ makes Mesa ask for DRM_PANFROST_PARAM_SYSTEM_TIMESTAMP_FREQUENCY etc. 1.5 adds JM contexts / priorities, 1.6 adds WB_MMAP + coherency; keep at 1.2.

### Ioctls (DRM_COMMAND_BASE + n, `include/drm-uapi/panfrost_drm.h`)
Needed for screen creation + minimal GLES2 draw:
1. GET_PARAM (0x04): all of these are queried at `panfrost_dev_query_props` (required=true, but missing params just return 0/default outside of asserts):
   GPU_PROD_ID, GPU_REVISION, SHADER_PRESENT, TILER_FEATURES, MEM_FEATURES, MMU_FEATURES, L2_FEATURES, TEXTURE_FEATURES0..3, AFBC_FEATURES, MAX_THREADS, THREAD_MAX_WORKGROUP_SZ, THREAD_FEATURES, THREAD_TLS_ALLOC. Optional (only if driver version >= 1.3 / 1.5 / 1.6): SYSTEM_TIMESTAMP(_FREQUENCY), ALLOWED_JM_CTX_PRIORITIES, SELECTED_COHERENCY. Fill from kbase `gpu_props` (TILER_FEATURES G71 etc). Mesa derives tile bins, bus width (L2_FEATURES[31:24]), core count (popcount SHADER_PRESENT) from these. Wrong TILER_FEATURES -> bad tiler heap sizing.
2. CREATE_BO (0x02): in `{u32 size, u32 flags}`, out `{u32 handle, u64 offset}`. Flags: `PANFROST_BO_NOEXEC=1` (set when not shader memory), `PANFROST_BO_HEAP=2` (tiler heap: allocate on fault; S9 kernel just commits the whole buffer, acceptable; heap is 128 MiB with PAN_BO_GROWABLE, `pan_device.c:103`), WB_MMAP=4 (only if version>=1.6). `offset` = GPU VA chosen BY THE KERNEL (Mesa uses `panfrost_kmod_vm_bind` -> `ops[i].va.start = panfrost_bo->offset`; it rejects any non-AUTO_VA and partial BO mapping). Rules: nonzero, whole BO mapped, page aligned, valid for handle lifetime, in range 0x2000000..4 GiB (`PANFROST_KMOD_VA_START/END` in `panfrost_kmod.c`, and `PAN_VA_USER_START 0x2000000` in `pan_device.h`), and EXECUTABLE BOs (no NOEXEC flag) are shader code. [G] Bifrost needs some descriptors/shaders in the same 4 GiB region so a single 32-bit VM is right.
3. MMAP_BO (0x03): returns `offset` for `mmap(fd, offset)`. Our shim replaces it with direct IOConnectMapMemory64 of the whole BO (S9+ `hakios_drm_map`, whole-BO only, enforced in `pan_kmod.h` patch). Needed: CPU mapping that is coherent with GPU (uncached/write-combined or cache sync on submit/wait).
4. SUBMIT (0x00) `struct drm_panfrost_submit` (40 bytes: jc u64, in_syncs u64, in_sync_count u32, out_sync u32, bo_handles u64, bo_handle_count u32, requirements u32, jm_ctx_handle u32, pad u32). Semantics: `jc` = GPU VA of first job descriptor of the chain (vertex/tiler/compute and the fragment job at the end; one chain per submit, Mesa serialises tiler+fragment under `dev->submit_lock`, `jm_submit_batch`). `bo_handles` = every BO the chain touches (descriptor pools, tiler heap `dev->tiler_heap`, sample positions BO always included) -> kernel keeps them resident/in MMU. `requirements`: bit0 FS (fragment), bit1 CYCLE_COUNT. `out_sync`: syncobj to receive the completion fence. `in_syncs`: only from imported sync fds (not used for GLES without EGL fences). `jm_ctx_handle`=0 default (JM_CTX_CREATE only called if context requests low/high priority). On the kernel side map the job chain to kbase atoms (JS0 for vertex/tiler/compute, JS1 for fragment, with dependency from fragment on tiler) [G, standard Panfrost practice; the S9 kernel did "one chain at a time in order"].
5. WAIT_BO (0x01) `{u32 handle,u32 pad,s64 timeout_ns}`; timeout is ABSOLUTE CLOCK_MONOTONIC ns (Mesa passes 0 or INT64_MAX or abs deadline); return 0 if idle else error ETIMEDOUT/EBUSY. (S9+ converts to relative in `wait_buffer`.) Used by BO cache / mapping readback.
6. MADVISE (0x08): `{handle, madv, retained}`; can answer `retained=1` always (S9 'HMD' local answer).
7. GEM_CLOSE (generic DRM ioctl via `drmCloseBufferHandle`).
8. Sync objects (libdrm calls, not DRM_COMMAND ioctls): `drmSyncobjCreate/Destroy/Reset/Wait/ExportSyncFile/ImportSyncFile` (used by `pan_context.c`, `pan_fence.c`, `pan_jm.c`). S9+ implements them in userspace as job sequence numbers (`syncobjs[]` = last job seq, wait by seq since jobs complete in order). Sync-file export = dup of /dev/null with a seq side table. The same code works for G71 if the kernel hands back a job number from SUBMIT.
9. Prime/import: `drmPrimeFDToHandle` is used for IOSurface import (`pan_bo.c`, `pan_kmod_bo_import`); only needed for the compositor path of sharing with the display, not for the first triangle. `drmPrimeHandleToFD` and timeline syncobjs may return ENOSYS.
10. Optional/ignorable (return 0/ENOSYS safely): SYNC_BO (0x0c, only used when the kmod advertises PAN_KMOD_DEV_FLAG_MMAP_SYNC_THROUGH_KERNEL; panfrost kmod does not set it) [G], SET_LABEL_BO (0x0a... only if debug labels), GET_BO_OFFSET (only for imported BOs: returns VA of an imported handle: needed iff importing IOSurface BOs), JM_CTX_CREATE/DESTROY, PERFCNT_*, QUERY_BO_INFO.

### What Mesa decides vs kernel
- GPU VA: KERNEL decides (BO offset returned by CREATE_BO / GET_BO_OFFSET). Mesa never passes a VA in. `PAN_KMOD_VM_*` ops are emulated locally by `panfrost_kmod_vm_bind`; only one VM per device; only AUTO_VA, MAP/UNMAP (unmap no-op; mapping released at GEM_CLOSE).
- Tiler heap: Mesa allocates a 128 MiB BO flagged HEAP|invisible, shared by all contexts. Kernel must either grow-on-fault (Linux) or back it fully (S9+). On G71 the kernel/firmware must set the tiler heap properties itself (Mesa only references the VA in the tiler descriptor).
- Mesa expects GPU-side faults to hang/timeout and relies on the kernel to reset the GPU.

### What carries over from the S9+ shim (G72 -> G71)
`ref\s9plus\baseline-support\hakios-drm\hakios.drm.c` (794 lines) is GPU-agnostic [E]: it only uses `drm_panfrost_*` structs and IOKit selectors (the request number = low byte of the ioctl, `IOConnectCallStructMethod`), services table ("panfrost" -> "HakiosMali", 1.2), `HAKIOS_MALI_WAIT 0x7d`, `HAKIOS_GPU_SURFACE 0x7e`, whole-BO mapping via `IOConnectMapMemory64`, syncobjs as job numbers. Everything carries over unchanged. G71-specific work is entirely in OUR kernel driver: GPU_ID/props (GET_PARAM), 20-core power-up, G71 MMU/AS setup, job manager (JS) interface which on G72 vs G71 are both Bifrost JM; and correctness of tiler heap/L2 config. Optional S9 extras (HFT fast trap, HWC completion cache, HMD, HMC) are env-flag opt-ins and can be dropped. Their `mali_fast.h` is irrelevant.

## (6) Go / no-go and first three checks

GO for a Mesa-based GLES path on G71, risk moderate: source support is present and shares ~everything with G72 which S9+ already runs, but G71 specific paths (no FP32 transcendentals, tilebuffer size, thread/core props, MP20) have no upstream CI.

First three things to verify:
1. GET_PARAM reply table and model match: have our driver return real kbase values (GPU_PROD_ID, REVISION, SHADER_PRESENT with 20 bits set, TILER/MEM/MMU/L2/TEXTURE_FEATURES0..3, THREAD_FEATURES, MAX_THREADS) and run Mesa's screen creation / `PAN_MESA_DEBUG=` printing renderer string; expect "Mali-G71 MP20 (Panfrost)". For 25.0.7 PROD_ID must read 0x6000 (not 0x60a0), for 26.3.0 0x60a0 (see (1)). Failure mode: "Unsupported model".
2. BO + VA contract on the XNU driver: CREATE_BO gives kernel-chosen nonzero VA in 0x2000000..4 GiB, whole-BO mapping works via IOConnectMapMemory64, CPU/GPU coherence; tiler heap 128 MiB HEAP allocation succeeds. Smoke test: allocate BOs, write via CPU, run a "write value" job / WRITE_VALUE job (Mesa `jm_emit_write_value`) and read back.
3. One minimal job chain end to end: clear-only frame (fragment job) then a single triangle via OSMesa/GLES2 (as `core/tools/mali-drmshim/gl_drmshim.c` does) with `PAN_MESA_DEBUG=trace,sync` (pandecode) to confirm job descriptors, submit flags (FS requirement), tiler heap use and fault-free completion on G71 hardware, then try a shader with exp2/log2/sin (G71's BIFROST_NO_FP32_TRANSCENDENTALS path) and a texture + blend pass representative of the compositor.
